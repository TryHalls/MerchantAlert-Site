Security by boundary

Keep the promise narrow, keep the data path visible.

The validation site is intentionally small: no third-party scripts, no embedded trackers, no credentials, and no pretend onboarding.

Static websiteCloudflare Pages-ready with security headers.
Marketing dataNo collection until the contact channel is configured.
Production secretsNever stored in this repo or front-end code.
Connected accountsRequires a reviewed onboarding and permission model.

Current controls

  • Static HTML, CSS, and JavaScript with no runtime dependency or external analytics.
  • Cloudflare Pages security headers in _headers, including content-type protection, clickjacking protection, referrer policy, and a same-origin content security policy.
  • Contact form defaults to a no-send state until an owner-controlled inbox is configured.
  • Documentation explicitly tells prospects not to share API keys, OAuth secrets, service-account files, payment details, or identity documents through the public form.

Production onboarding still required

Before connecting a real Merchant Center account, the operator must complete the Google account, developer registration, OAuth or service-account authorization, secret storage, access revocation, audit logging, incident response, retention, and customer support decisions in the backend lane. This site does not create or claim any of those credentials.

Security contact

A real security contact must be configured before the site claims to accept vulnerability reports. Until then, do not publish an invented security address. See the launch checklist for the exact owner action.
